# AGENTS.md

Vendor-neutral instructions for coding agents. 倉庫層規範（Layering、Contract、Safety、buf）見根 `AGENTS.md`；本檔只管 `services/platform/`。

## Project

- **Name:** platform（`services/platform`；倉庫為 `env-law`）
- **Role:** 多租戶控制平面（control plane）：tenants, API keys, rate limiting, usage metering, public REST API. Calls `services/ontology` (Python, shared non-tenant data) and `services/consult` (grounding evidence, tenant-scoped) over gRPC.
- **Stack:** C# / .NET 10 (SDK pinned in `global.json`) · ASP.NET Core · PostgreSQL · xUnit
- **Auth:** API keys only for now (OIDC later for an admin UI)
- **Billing:** not integrated yet; plans assigned manually. Note: Stripe does not onboard Taiwan entities — evaluate Paddle / local gateways when needed.
- **Status:** tenants + API keys, per-tenant rate limiting, usage metering, REST facades over the ontology and consult gRPC services

## Architecture

- Modular monolith: one solution, one deployable; modules as projects (`Modules.Tenancy`, `Modules.ApiAccess`, `Modules.Metering`, …).
- Two DbContexts, no more: `TenancyDbContext` (Finbuckle requires the EFCore tenant store to derive from `EFCoreStoreDbContext`, so it cannot share) and `PlatformDbContext` in `EnvLaw.Platform.Data` for all tenant-owned data (schema `platform`). A new tenant-owned entity goes into `PlatformDbContext`; modules do not get their own contexts — each extra context is another migration set, bundle and Job step, and no cross-module transaction.
- Data Protection keys (cookie and antiforgery protection) are stored in `TenancyDbContext` (`tenancy."DataProtectionKeys"`, `AddPlatformDataProtection`, fixed ApplicationName `env-law-platform`), not in `PlatformDbContext`: they belong to no tenant, and `PlatformDbContext` cannot be built before tenant resolution while the key ring loads at host start. Without shared keys a cookie signed by one replica is rejected by another. The keys are plaintext XML in the database; add `ProtectKeysWith…` if at-rest encryption is required. Not registered while generating the OpenAPI document (no database there).
- Blazor Server circuits are stateful SignalR connections: running more than one replica needs session affinity on the ingress (deploy repo) or an external backplane. Not configured yet.
- Multi-tenancy is runtime isolation (tenant resolution + `TenantId` query filters), never per-tenant code or repos.
- When billing is integrated, the provider is the source of truth for payment; this service will keep an entitlements table updated via its webhooks.

Public REST contract: `openapi/openapi_v2.json`, generated on every `dotnet build` (`Microsoft.Extensions.ApiDescription.Server`; `PlatformOpenApi.cs` keeps only `/v2`, declares the API-key scheme and the 401/429 every endpoint shares). Commit it with the code change; CI fails when it is stale (`dotnet` job) and when it breaks the target branch's version (`openapi` job, oasdiff). A new `/v2` endpoint gets `.WithName` / `.WithTags` / `.WithSummary` / `.WithDescription` and a `.Produces…` per status it returns. An incompatible change goes to a new version group (`/v3`), not into `/v2`. Build-time generation runs `Program.cs` against a mock server; the only branch for it is the placeholder config at the top of `Program.cs`.

The public contract has its own names, independent of the internal gRPC ones (the endpoints map between them): legal vocabulary from ELI and Akoma Ntoso — `pointInTime` (an expression's point in time; gRPC `as_of`), `authorities` (gRPC `citations`), `authorities[].citation` (formal citation; gRPC `label`), `authorities[].uri` (an ELI-template URL, not an official ELI; gRPC `iri`), `basis` `direct`/`indirect` (gRPC `confidence`), `outcome` `grounded`/`refused`, refusal reason `no_authority`. A new public field takes its legal term first; the internal proto does not have to follow.

Contracts: `Modules.Ontology` compiles the repo-root `proto/env_law/ontology/v1/ontology.proto`, `Modules.Consult` compiles `proto/env_law/consult/v2/consult.proto` (Grpc.Tools; see each `.csproj`). Never copy a `.proto`.

Configuration is read in one way: each setting group is an `IPlatformOptions` class that names its own section and is registered with `AddPlatformOptions<T>()` (bind + `ValidateOnStart`); consumers inject `IOptions<T>`. Nothing else touches `IConfiguration` (`Program.cs` no longer does) except the one OpenTelemetry switch in `Observability.cs` (`OTEL_EXPORTER_OTLP_ENDPOINT`, a standard key that decides whether an exporter is registered at all), so a wrong or missing value stops the host at startup with the key named — in k8s a CrashLoopBackOff with a clear message — instead of failing on the first request. The groups: `DatabaseOptions` (`ConnectionStrings`, SharedKernel), `OntologyOptions` / `ConsultOptions` (`Ontology` / `Consult`, via `AddInternalGrpcClient`), `ApiAccessOptions` and `PlatformHostOptions` (both `Platform`, each reading its own keys), `UiOptions` (`Platform:Ui`). A new group: implement `IPlatformOptions`, register it, add an `IValidateOptions<T>` (`[OptionsValidator]` when attributes are enough, hand-written for cross-field rules), and add a case to `ConfigurationTests`. Key names are the contract with the deploy repo: renaming one is a breaking change. In k8s a ConfigMap or Secret supplies them as environment variables (`Section__Key`; the secret ones are listed below).

Config (`Ontology` section): `Address` (in-cluster `dns:///env-law-ontology:50051` — headless Service, calls round-robin across pods; a plain `http://` address is a single host), `InternalToken` (must equal the service's `ONTOLOGY_INTERNAL_TOKEN`; secret), `Timeout`. Development uses `http://localhost:50051` + token `dev` (`ONTOLOGY_INTERNAL_TOKEN=dev uv run env-law-ontology` in `services/ontology/`).

Config (`Consult` section): same keys (`Address` in-cluster `dns:///env-law-consult:50052`; `InternalToken` = the service's `CONSULT_INTERNAL_TOKEN`; `Timeout`, default 10 s because consult itself calls ontology). Development uses `http://localhost:50052` + token `dev`. Both sections are required at startup. Both clients are registered by `SharedKernel.InternalGrpcClient.AddInternalGrpcClient` (internal token, tenant/request metadata, round-robin, h2c) — a new internal service client goes through it, not a copy.

Config (`Platform` section): `AdminKeySha256` (hex SHA-256 of the operator key; set via environment variable `Platform__AdminKeySha256`, never commit; the Api project has no `UserSecretsId`), `Plans:<name>:PermitLimit`/`Window` (the repo defaults are `standard` 60/min and `pro` 600/min; there is no built-in plan), `TenantPlans:<tenant identifier>` = plan name (an unknown plan name fails startup; **a read-only fallback** — the real assignment lives in the database, see below), `DefaultPlan` (the plan of any tenant not listed; **leave it unset in production**: the service is fully paid, so a tenant without a plan gets 402 on the data endpoints — see below; Development and the tests set it so freshly created tenants work), `ApplyMigrationsOnStartup` (Development/tests only), `SeedDevelopmentData` (Development only, on in `appsettings.Development.json`, off in the shared test host: on startup, after migration, `DevelopmentSeed` creates tenant `dev` and its first Owner `owner@example.test` **only if the tenant has no members**, through the same `ITenantProvisioner`/`IMemberAdmin` the operator path uses, audited as actor `system`; the one-time password goes to the terminal once via `Console.WriteLine`, never `ILogger`; there is no default password and a non-Development environment ignores the setting even when it is on; `DevelopmentSeedTests` run each case on a fresh database in the test container, because the shared one must not gain a `dev` tenant; Development also sets `Platform:Portal:RequireMfaForAdmins=false` so the seeded Owner can be used without an authenticator). Connection string: `ConnectionStrings:Platform`; Npgsql also reads `PGUSER`/`PGPASSWORD`, so a deployment keeps the password out of the string.

Config (`Platform:Ui` section): `Google:ClientId` / `Google:ClientSecret` (env `Platform__Ui__Google__ClientSecret`, never commit; **optional**: if either is unset outside Development the operator UI is simply not served — `/ui` is 404, a warning is logged, and the API starts normally, because a Secret often arrives after the code that reads it and a missing UI credential must not keep the whole service from starting), `OperatorEmails` (list; empty = nobody can sign in), `AllowedHostedDomain` (optional Workspace domain). Register `https://<host>/signin-google` as an authorized redirect URI in the Google Cloud OAuth client (local: `http://localhost:<port>/signin-google`). Behind a TLS-terminating proxy set `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` on the container, otherwise the redirect URI is built as `http://` and Google rejects it.

Observability (`Api/Observability.cs`): OpenTelemetry traces (ASP.NET Core, HttpClient — which covers the gRPC clients — and Npgsql), metrics (plus .NET runtime) and logs. All configuration is the standard `OTEL_*` keys, so a k8s ConfigMap or the Downward API can set them as environment variables: nothing is exported unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set; `OTEL_SERVICE_NAME` defaults to `env-law-platform` in `appsettings.json` and the environment overrides it; sampling is `OTEL_TRACES_SAMPLER` / `OTEL_TRACES_SAMPLER_ARG`; pod identity goes in `OTEL_RESOURCE_ATTRIBUTES` (e.g. `k8s.pod.name=$(POD_NAME)`). The authenticated tenant is tagged `tenant.id` on the request trace only, never on metrics (unbounded cardinality). Console logs are JSON on stdout outside Development (`Logging:Console:FormatterName`). Probes: `/health/live` checks nothing (a dependency outage must not restart the pod), `/health/ready` checks the database (`TenancyDbContext`, which exists before tenant resolution) and returns 503 when it is down; `/health` is kept as an alias of liveness. Probe requests are not traced. The deploy repo should point `readinessProbe` at `/health/ready` and `livenessProbe` at `/health/live`.

Audit log (`Modules.Audit`, `Data/AuditEvent.cs`, contracts in `SharedKernel/Audit.cs`): `platform."AuditEvents"` is append-only, enforced by database triggers (UPDATE, DELETE, TRUNCATE raise), not by convention; tests run raw SQL against it. Who is derived from the authenticated identity (`AuditActors`: `operator-key` for the shared admin key, `operator-user` for a Google operator, `tenant-key` with the API key id, `anonymous`), never from the request body. Events about a tenant carry `SubjectTenantId`; the entity is deliberately not a Finbuckle tenant entity (operators read across tenants), so every read filters explicitly. Two ways to write: `db.StageAudit(...)` adds the event to the caller's `PlatformDbContext`, so it is saved in the same transaction as the change (API key issued and revoked work this way: no change, no event; no event, no change); `IAuditLog.AppendAsync` writes on its own for events with no change to attach to — `tenant.created` (the tenant store is a different DbContext, so this one is not atomic: a failed append returns 500 after the tenant exists) and operator sign-in, denied sign-in and sign-out (fail closed: a failed append stops the sign-in). `Detail` never holds a secret, a hash or a full API key (a test checks). Each event keeps the OpenTelemetry trace id. Read with `GET /admin/audit-events?tenant=&action=&actor=&before=&limit=` (newest first, keyset cursor on the time-ordered UUIDv7 `Id`, max 200 per page). Known limits: the table owner or a superuser can still drop the triggers, so the application's database role must not own the table; no retention or partitioning yet; the append-only guarantee says nothing about events that were never written.

Design system (`Web/Design/`): one source for the look, aligned with the chepb family (`chepb-envkm/designs`, frontend `styles/tokens`): brand green `#006030`, slate neutrals, status colours that are text-grade (≥ 4.5:1 on white and on their own 10 % tint), flat surfaces, no gradients (a test fails if one appears). `DesignTokens.cs` holds the colours (semantic names, **light only** — the product decision is no dark theme: `color-scheme: light` is declared, so the page stays light when the system is set to dark, and a test fails if any `prefers-color-scheme` rule comes back; one role, one colour: tints and borders are `color-mix` of the role colour in CSS, not extra tokens), the type scale (system font stack with Traditional Chinese faces — deliberately not bundled web fonts, unlike chepb, because layout identity across operating systems matters for statute text there, not here; body tiers are 1 px above the usual defaults for long reading, size-specific tracking and leading, `rem` so the layout follows the user's text size), spacing, radius (control 8, card 12, sheet 16, pill), elevation, and motion (durations named by interaction: `fast` 150 ms feedback, `normal` 200 ms enter/exit, `slow` 300 ms large moves, `reveal` 500 ms; easing named by the role of the movement — `standard`, `enter`, `exit`, `move` — orthogonal to duration; press feedback is instant on press and `--ep-press-scale` 0.97 springs back on release, critically damped, no bounce because nothing here is dragged). Responsive: two viewport breakpoints only, `DesignTokens.Breakpoints` — tablet `48rem` (768 px) and desktop `80rem` (1280 px), in `rem` and written in range syntax (`(width < 48rem)` is phone); CSS cannot read variables in a media query, so a test fails if the stylesheet uses any other viewport width (component container queries, which follow the container, are exempt); touch targets are `--ep-touch-target` (44 px) under `pointer: coarse`. `TokenCss` renders them as `--ep-*` CSS variables into the page head — including the user-preference overrides, which live in the tokens rather than per component (`prefers-contrast: more` deepens the hairline and secondary text, `prefers-reduced-motion` sets the press scale to 1) — `PlatformTheme` builds the MudBlazor theme from the same values, and `wwwroot/design/platform.css` only references the variables (tests fail if it hard-codes a colour, a duration, an easing, a scale or the touch size). `DesignTokenTests` checks every text pairing for WCAG AA contrast (4.5:1, including status colours on their tints; control borders and focus ring 3:1). Change a colour or size in `DesignTokens.cs` only. Shell: `MainLayout` (translucent app bar, drawer nav, skip link) for the operator, `PortalLayout` (static, no MudBlazor) for customers, `AnonymousLayout` (one centred card) for signed-out pages; pages use `PageHeader` and `EmptyState` instead of laying out their own titles. The nav lists only pages that exist.

Operator pages (`Web/Components/Pages/`): `/ui/tenants` (searchable, sortable list; plan chip with an icon so the state is not carried by colour alone; "新增租戶" dialog; links to the detail page and the tenant's audit trail), `/ui/tenants/{id}` (assign/change/remove the plan; list, issue and revoke API keys; the tenant's last 10 audit events) — the actions call `ITenantProvisioner`, `IPlanAdmin` and `IApiKeyAdmin`, the same services behind `/admin`, with the signed-in operator's `ClaimsPrincipal` as actor, so the audit trail names the person (their email), not a shared key. A newly issued key is shown once in a dialog that Esc and a backdrop click cannot dismiss (only 「我已保存」), and the UI never re-renders it; revoking and removing a plan ask for confirmation (they cannot be undone / cut the tenant off at once), assigning and issuing do not. The dialogs have no automated click tests (the project has no browser tests); the services and the server-rendered pages are tested, the dialog flow was checked by hand in a browser. Fields use explicit `OnClick`/`OnKeyUp`, not `EditForm` + an external `form=` button (that submit did not fire reliably inside MudBlazor's dialog), and `Immediate="true"` so Enter sees the latest text and `/ui/audit` (filters above the table, newest first, expandable rows for the detail JSON and trace id, a "load more" button instead of infinite scroll — infinite scroll fails accessibility audits — over the keyset cursor). Filter state lives in the URL (`?tenant=&action=&actor=`), so a link can be shared and a reload keeps it. Pages never call the `/admin` HTTP API with an admin key: they read `IAuditQuery` and `ITenantDirectory` (contracts in `SharedKernel`; the audit module and the composition root implement them, and `GET /admin/audit-events` uses the same `IAuditQuery`). Both open their own scope per call, because a Blazor Server circuit lives far longer than a request and must not hold a stale `DbContext`. Times are shown in Taipei time (fixed UTC+8, Taiwan has no DST, so no tzdata needed) with the ISO time in `title`. Long ids are shortened to their **end**: they are UUIDv7, whose start is a timestamp and identical for ids made close together. The table uses real `table/th scope` markup, a labelled table, `aria-expanded` on the row toggles and an `aria-live` status line. Design basis (Material data tables, IBM Carbon data table, Google Logs Explorer behaviour, GitLab's accessibility audit of infinite scroll) is in the MR that introduced the pages; no Google design-guideline page was found, so the Google part rests on documented Logs Explorer behaviour only.

Responsive (native CSS, `wwwroot/design/platform.css`, no JS and no breakpoint library): the table card is a **container query** container (`container: ep-table / inline-size`), so the layout follows how wide the card is, not the screen; under 36rem a table becomes one small card per row (header hidden but kept for assistive tech, `data-label` supplies the field names), above it the table scrolls inside the card if it must. Breakpoints are in `rem` so a larger browser text size switches to the narrow layout sooner. Never put `overflow: hidden` on the card: it clips the right-hand columns of a wide table so they can be neither seen nor scrolled to (a test fails on it). `@media (pointer: coarse)` lifts tap targets to 44px; hover styles live in `@media (hover: hover)`; `viewport-fit=cover` plus `env(safe-area-inset-*)` handle notches; `theme-color` follows the theme and comes from the tokens; the two largest type sizes are `clamp()`. Zoom is never disabled. Checked in a browser at 320, 375 and 768 px with no horizontal page scroll (WCAG reflow). Known limit: in card mode the column sort control is not shown (search still works).

`Api.csproj` sets `RequiresAspNetWebAssets` because the Razor components live in `EnvLaw.Platform.Web` (a class library) and the host has no `.razor` file of its own: without it the SDK does not ship `_framework/blazor.web.js`, the browser gets a 404, the interactive circuit never connects, and nothing looks wrong in the server-rendered HTML. `DesignPageTests.TheScriptsThePageReferencesAreServed` fetches every script a page references for exactly this reason.

Production migrations: EF Core migration bundles (the form EF Core's docs recommend for automated deployment), built into the image as `/app/migrate/tenancy` and `/app/migrate/platform` and run in that order by the deployment's migration Job. Each context has an `IDesignTimeDbContextFactory` sharing its `UseNpgsql` configuration with the app (`…Module.Configure`), so a bundle builds the context without running `Program.cs` and targets the same migrations history table.

## Auth & tenancy flow

- Tenant API: `Authorization: Bearer sk_live_{prefix}_{secret}` → `ApiKeyAuthenticationHandler` (lookup by prefix, SHA-256 + constant-time compare) → `tenant` claim → Finbuckle resolves tenant → tenant-owned entities (`IsMultiTenant()`) are filtered automatically.
- Operator API (`/admin`): `X-Admin-Key` header, compared against `Platform:AdminKeySha256`.
- Operator UI (`/ui`): Google SSO (`AddGoogle`, PKCE) → `UiCookie` cookie. Google only proves identity; `OperatorAllowlist` decides access (`email_verified` + `Platform:Ui:OperatorEmails`, optional `AllowedHostedDomain`) both at sign-in (`OnTicketReceived`: not allowed → no cookie, `/ui/denied`) and on every request (`OperatorHandler`, so removing an email takes effect immediately). The default scheme stays ApiKey, so `UsePlatformWebAuthentication` authenticates `/ui` and `/_blazor` (SignalR, no policy) with the cookie itself. Pages in `Components/Pages/` are `[Authorize(Policy = UiPolicy)]` by default via `_Imports.razor`; public pages go in `Components/Anonymous/`. Logout is a POST with an antiforgery check done in the handler (endpoint metadata did not enforce it). The cookie never authenticates `/v2` or `/admin`.
- Customer portal (`/portal/{tenant}/…`, project `Modules.Members`, pages in `Web/Components/Portal/`): username-and-password sign-in for the people of a tenant. **Demo grade, off by default** (`Platform:Portal:Enabled`; always on in Development; outside it `/portal` is a 404 and no cookie is ever issued): there is no external or SSO sign-in and the second factor is TOTP only (no passkey; required for Owner and Admin — see MFA below), no email (so no invitation, forgotten-password or email confirmation), a per-source-address limit on sign-in and password-change submissions (`Platform:Portal:SignInAttemptsPerMinute`, default 60 a minute — generous on purpose, because an agency or a consultancy often sits behind one shared outbound address and a whole office signing in at nine must not be blocked; it stops automated guessing, not normal use — sliding window, only POSTs, successes count too; `PortalRateLimit`) on top of account lockout, but no CAPTCHA or per-account throttle, and the initial password passes through an operator. Not for real customers until those exist (`env-law-docs` 07-01 §5, §7). The limit keys on `RemoteIpAddress`, so behind a proxy the forwarded headers must be honoured (`ASPNETCORE_FORWARDEDHEADERS_ENABLED=true`) or every customer shares one allowance; its state is per replica (N replicas allow N times as many); the test host has a single address, so tests prove the quota and its timing, not that different sources get separate quotas. Model (A) of 07-01: ASP.NET Core Identity on `PlatformDbContext` (`MultiTenantIdentityDbContext<ApplicationUser>`, migration `CustomerUsers`), so users are tenant entities — the same email in two tenants is two accounts, and a tenant filter hides other tenants' users. The tenant is in the path (resolved before sign-in by the delegate strategy in `TenancyModule`, path first, API-key claim second). Pages are **static SSR** (`[ExcludeFromInteractiveRouting]`, no circuit): each request resolves its own tenant and authenticates itself, the form is a plain POST with antiforgery; `App.razor` picks the render mode per page. Passwords: Identity's PBKDF2 hasher, minimum 12 characters and no composition rules (NIST SP 800-63B), 5 failures lock the account for 15 minutes, and a failed sign-in never says whether the email exists or the account is locked (one message; an unknown email still pays for one hash). A failed form never echoes a password back into the HTML (a test checks). The operator creates a member (`IMemberAdmin`, tenant detail page): a random 16-character one-time password is shown once and stored only as a hash; the member must change it on first sign-in (`MustChangePassword` → `pwd_change_required` claim → only the password page opens; an operator reset sets it again). The session is its own cookie (`EnvLaw.Portal`, scheme `Identity.Application`, the name `SignInManager` signs in with) carrying user id, role and `tenant` claims; authorization reads only claims (`PortalMemberHandler`: the cookie's tenant must equal the tenant the request path resolved to, and a pending password change only opens the password page). The security stamp is checked on every portal request (`PortalSessionValidator`, not Identity's `SecurityStampValidator`, whose failure path signs out Identity schemes we do not register and returns 500), so a password change or reset ends the member's other sessions at once. Three things that bit during the build, kept as rules: (1) the portal cookie is authenticated by `UsePlatformPortalAuthentication`, **after** `UseMultiTenant` — authenticating earlier resolves the scoped `PlatformDbContext` before the tenant is known and the whole request keeps a tenant-less context (NullReference in the tenant query filter); (2) the tenant context is an `AsyncLocal`, so `MemberAdmin` binds it in the calling method, never inside an async helper (the value is discarded when the helper returns); (3) the tenant-match check in the handler is hidden end to end by the user table's tenant filter, so it has its own unit tests (`PortalMemberHandlerTests`, each check mutation-tested). Audit: `portal.signed_in`, `portal.sign_in_failed`, `portal.password_changed`, `portal.signed_out`, `member.created`, `member.password_reset`; the actor is `tenant-user` (the user id). A failed sign-in records the member id when the email exists and a reason, never what was typed (people paste passwords into the email box, and the table is append-only). Roles are `CustomerRoles` (a column, not Identity roles); the role table in 07-01 is a draft, not agreed with customers. The portal home shows the organisation, plan and API key prefixes (Owner, Admin and Developer only).
- Portal MFA (TOTP, RFC 6238; `IPortalTwoFactor`, `PortalTwoFactor`, `TotpVerifier`, `MfaPendingCookie`; pages `login/mfa` and `security`): a member enrols at `/portal/{tenant}/security` (QR drawn server-side with `Net.Codecrete.QrCodeGenerator`, the key never leaves for a third-party QR service; the secret is also shown as groups of four for manual entry), confirms with a code, and gets 10 one-time recovery codes **in that one response only**. Sign-in then has two steps: the password (`RequiresTwoFactor`) issues only a 5-minute, non-sliding `EnvLaw.PortalMfa` cookie — a different scheme that the portal's authorization does not accept — and the second page turns a code (or a recovery code) into the real session. Rules that are tested and must stay: (1) **one failure counter** for password and code, and a correct password does **not** reset it for an MFA member (`PortalAccount` does its own lockout bookkeeping instead of `PasswordSignInAsync`, which resets on success); otherwise someone who knows the password could re-enter it each round and guess six digits forever; (2) **replay guard**: only a time step newer than `LastTotpStep` is accepted, updated atomically (`UPDATE … WHERE LastTotpStep < @step`), so an observed code cannot be reused inside its 30 seconds; clock tolerance is ±1 step and time comes from `TimeProvider`; (3) the key is generated and stored by us (`SetAuthenticationTokenAsync`), **not** `ResetAuthenticatorKeyAsync`, which also rotates the security stamp and would end the very session that opened the page; (4) the pending ticket is bound to the tenant that issued it; (5) every `/portal` response is `Cache-Control: no-store`; (6) no key, code, recovery code or `otpauth` URI reaches the audit trail or any log (a test captures both). Operators reset a member who lost both the device and the recovery codes with `IMemberAdmin.ResetTwoFactorAsync` (tenant page, with a confirmation that tells them to verify the person first): it disables the factor, deletes the key and codes, ends all sessions and is audited (`member.mfa_reset`). **Required for Owner and Admin** (`Platform:Portal:RequireMfaForAdmins`, default `true`; the shared test host sets it `false` so the other tests are not forced to enrol, and `PortalMfaRequiredTests` turns it on): the claims factory adds `mfa_enrollment_required` to the session of an Owner or Admin who has not enabled it, and policy `Portal` rejects that session, so such a member can open only the password page and `/security` (`PortalEnrollment`). The order is fixed: **change the operator-issued password first, then enrol**, so the factor is never set up behind a password an operator knows; the access-denied redirect sends a member to the first thing still pending. A role that is required cannot turn it off (the page hides the form and the service refuses), and an operator reset sends a required member back to enrolment on the next sign-in rather than leaving them unprotected. An ordinary member can turn it off with the current password **and** a code (either alone is refused, and both failures count toward the lockout), and any member can regenerate the ten recovery codes with a code (the old ones stop working; `portal.mfa_disabled`, `portal.recovery_codes_regenerated` are audited). Interop was checked once in a real browser with a code computed by an independent RFC 6238 implementation (Python), not only Otp.NET against itself; **scanning the QR with a real authenticator app was not tested**. Known limits: the TOTP key and the recovery codes are stored as Identity stores them, in plaintext in the database (the Data Protection key ring is plaintext there too, so encrypting them with it would add nothing; fix with at-rest encryption or a KMS-held key); no passkey.
- Member management by the customer (`/portal/{tenant}/members`, `IMemberSelfService`, `MemberSelfService`, `MemberPolicy`): an Owner or Admin adds, disables and re-enables members, changes roles and resets passwords without an operator; the operator path (`IMemberAdmin`) and this one share `MemberCore` (validation, one-time password, audit), so they cannot drift. Rules, each tested: **hierarchy** — an Owner manages everyone; an Admin manages only Developer, Billing and Viewer, never an Owner or another Admin, and can grant only those roles (what you may manage is exactly what you may grant, so nobody is promoted above their manager); **nobody acts on themselves** (disable, role, reset), so an active Owner always remains *by construction* — only an active Owner can manage an Owner and cannot act on themselves, so the acting Owner is still there; the one hole is two Owners disabling each other at the same instant (both checks pass before either lands), which is not guarded and would need an operator; **the actor's role is read from the database, not from the cookie claim** (the claim may be stale); a member from another tenant is simply not found (the tenant filter). A **disabled** member (`ApplicationUser.Disabled`, migration `MemberDisabled`) cannot sign in (same generic failure as a wrong password, and the hash is still computed), loses every open session at once (security stamp rotated **and** the session check looks at the flag itself — a test sets the flag without touching the stamp), and cannot finish a second step started before the disabling; accounts and their audit trail are kept. A role change or a reset also rotates the stamp, so the old session ends and the new role (and any MFA requirement that comes with it) applies at the next sign-in. The one-time password of a new or reset member is shown once, in the response to the POST (no redirect), to the Owner or Admin who must hand it over; it is stored only as a hash. Audit: `member.created`, `member.password_reset` (now with a `tenant-user` actor when a customer did it), `member.disabled`, `member.enabled`, `member.role_changed` (previous and current role). One form wraps the whole table (buttons carry `disable:{id}` etc.; roles are `role-{id}` selects) because static SSR form names must be fixed; on a narrow screen the table stacks into one card per member. The operator can do the same through the tenant page and through `/admin/tenants/{id}/members` (GET list; POST create, `…/{userId}/password-reset`, `…/two-factor-reset`, `…/disable`, `…/enable`; `MembersAdminEndpoints`, admin key only): that is also how the **first member of a tenant is created without the operator UI** (no Google credentials needed). The create and reset responses carry the one-time password (once; not logged, not audited). A re-enabled member's old cookies must not come back: disabling and enabling both rotate the security stamp, and a test keeps a second session untouched between the two to prove it (the session that is *used* while disabled is signed out and loses its cookie, which would hide a missing rotation). Not done: no invitation by email, no bulk actions, no pagination of the list, and the page was looked at on a desktop and a 375 px screen, not on a real device.
- Plan assignment is data, not configuration: `platform."TenantEntitlements"` (tenant id → plan name; not a Finbuckle tenant entity, like `AuditEvents`). Plan *definitions* (limits) stay in `Platform:Plans` — a product decision that changes rarely; *who is on which plan* changes with every customer, so it is set by an operator at runtime (`PUT /admin/tenants/{id}/plan`, `DELETE …/plan`, `GET /admin/plans`, and the operator UI through the same `IPlanAdmin`), takes effect at once and is audited (`tenant.plan_assigned`, `tenant.plan_removed`, written in the same transaction as the row; assigning the plan a tenant already has is a no-op with no event). No redeploy per customer. Lookup order: database assignment → configured `TenantPlans` → `DefaultPlan`. Every request needs the plan, so `PlanCatalog` reads an in-memory snapshot: the replica that handled the change updates it at once, the others reload every `Platform:EntitlementRefresh` (default 10 s, at least 1 s) via `EntitlementLoader` — a keeps-the-last-snapshot-on-failure background service, registered by `AddEntitlementRefresh()` and not started by the OpenAPI generation host. An assignment to a plan that was later removed from configuration counts as *no plan* (fail closed, warning logged) instead of failing every request. The rate-limit partition key includes the plan name, so a plan change swaps the limiter and the new allowance applies immediately. Operators also manage a tenant's keys through `IApiKeyAdmin` (`GET`/`POST`/`DELETE /admin/tenants/{id}/api-keys[/{keyId}]`); revoking through another tenant's id is a 404 (the tenant query filter hides keys that are not its own), and a repeated revoke keeps the first time and is audited once. Known limit: removing the database assignment does not remove a plan that `TenantPlans` or `DefaultPlan` still gives the tenant.
- Fully paid, no free tier: a tenant needs a plan to call the data endpoints (`/v2/laws/…`, `/v2/search`, `/v2/ground`, group `PaidPolicy`); without one the answer is `402 Payment Required` (problem+json), decided in authorization, before rate limiting, so an unplanned tenant spends none of its limit. The management endpoints (`/v2/me`, `/v2/usage`, `/v2/api-keys`) stay open to any authenticated tenant — a customer without a plan must still see who it is, see its usage and revoke a stolen key — and are held to a floor of 20 requests/minute (`PlanCatalog.UnplannedFloor`), an abuse guard and not a service allowance. A paid trial or pilot is just another entry in `Plans` assigned to the tenant; nothing here needs to change for it. 402 is declared on exactly the data operations in `openapi_v2.json` (additive, so `oasdiff` stays green). Assignment is an operator action on `TenantEntitlements` (above) until billing exists; the target is entitlements written by payment (see the tenant lifecycle in `env-law-docs` 07-02).
- Middleware order is load-bearing: `UseAuthentication` → `UseMultiTenant` → `UseAuthorization` → `UseRateLimiter`.
- `GET /v2/laws/{id}` and `/articles` take an optional `asOf` (`YYYY-MM-DD`, omitted = current), passed to the ontology as `as_of`: the law title and the article list are those in force that day. A date with no version in force is a `404`, never the current text (the contract in `ontology.proto`: the current text would be indistinguishable from a correct answer); a value that is not a date is a `400`. Neither is metered. The date is not sensitive, so these stay GETs.
- Search has one implementation, `ILawSearch` (contract in `SharedKernel/LawSearch.cs`, `Modules.Ontology/LawSearch.cs`, scoped because metering needs the request's tenant): validation errors (`AdminStatus.Invalid`), an unavailable ontology (`Unavailable`), the `ontology.search` metering on success only, and "the query text reaches no log" live there once. `POST /v2/search` and the portal page `/portal/{tenant}/search` (static SSR, a POST form, policy `Portal`) both call it, so they cannot drift. The caller checks the plan (fully paid): the REST group does it in authorization; the portal page reads the tenant's plan from `ITenantDirectory` and shows no form without one (a posted form is not dispatched either; a test proves the ontology is never called). Every signed-in member except a pending-password session may search; roles only gate keys and members. The result shows each article with a copyable citation naming the law, the article number, the day searched (or 現行) and the ELI URI. The portal search has no rate limit of its own beyond authentication and metering. Not visually inspected with real results (the dev setup has no ontology service) and not tested end to end against the real ontology.
- `POST /v2/search` (body `{query, asOf?, limit?}`) is lexical article search over the ontology's `SearchArticles`, as of a date (omitted = current), 1–50 hits. It is a POST on purpose: a consultancy's query is the content of a client's matter, and a query string is written by the request log and by trace `url.query`. The query text must reach no log: `SearchTests.TheQueryTextIsNeverWrittenToTheLogs` captures every log and fails if it appears, and env-law-ontology logs only `query_chars=N` (`test_the_query_text_is_not_written_to_the_log`). Metering records the count (`ontology.search`), never the text. gRPC `InvalidArgument` (blank query, bad `asOf`, `limit` out of range) → 400. `score` is comparable only within one response.
- `/v2/laws/…` calls env-law-ontology over gRPC with `authorization: Bearer <InternalToken>`, `x-tenant-id`, `x-request-id`; gRPC `NotFound` → 404, `Unavailable`/`DeadlineExceeded` → 503. Only successful calls are metered (`IUsageRecorder`, one row per call in `platform.UsageRecords`).
- `POST /v2/ground` calls env-law-consult `Ground` the same way; a refusal is a 200 result and is metered (`consult.ground`); gRPC `InvalidArgument` → 400, `Unavailable`/`DeadlineExceeded` → 503 (not metered). Tests: `FakeConsultServer`.
- A `MultiTenantDbContext` captures the tenant at construction: never resolve it before tenant resolution; for a specific tenant outside a tenant request use `MultiTenantDbContext.Create<TContext, TenantInfo>(tenant, services)`.

## Conventions

- Formatting rules: `.editorconfig`.

## Safety

- Never commit secrets, connection strings, billing keys, or real `.env*` / local appsettings values.
- Every tenant-scoped query must be filtered by `TenantId`; never disable query filters without review.
- Bypass only the tenant filter by name (`IgnoreQueryFilters([TenantToken])`), and only in reviewed cross-tenant lookups (currently: API key authentication).
- Generated: `src/*/Migrations/` (change via `dotnet ef`, never by hand; marked `generated_code` in `.editorconfig`; the one exception is `AuditEventsAppendOnly`, an otherwise empty migration whose `Sql` calls are hand-written because EF cannot model triggers), gRPC code under `obj/` (from the repo-root proto), `openapi/openapi_v2.json` (from `dotnet build`; never by hand).
- Also ask before applying migrations to shared DBs (general ask-before list: root `AGENTS.md`).
