# AGENTS.md

Vendor-neutral instructions for coding agents. 倉庫層規範（Layering、Contract、Safety、buf）見根 `AGENTS.md`；本檔只管 `services/platform/`。

## Project

- **Name:** platform（`services/platform`；倉庫為 `env-law`）
- **Role:** 多租戶控制平面（control plane）：tenants, API keys, rate limiting, usage metering, public REST API. Calls `services/ontology` (Python, shared non-tenant data) and `services/consult` (grounding evidence, tenant-scoped) over gRPC.
- **Stack:** C# / .NET 10 (SDK pinned in `global.json`) · ASP.NET Core · PostgreSQL · xUnit
- **Auth:** tenant API keys (REST `/v2`); one shared operator key (`/admin`); operator accounts with password + mandatory TOTP (operator console `/ui`); customer-portal accounts (`/portal`)
- **Billing:** not integrated yet; plans assigned manually. Note: Stripe does not onboard Taiwan entities — evaluate Paddle / local gateways when needed.
- **Status:** tenants + API keys, per-tenant rate limiting, usage metering, REST facades over the ontology and consult gRPC services

## Architecture

- Modular monolith: one solution, one deployable; modules as projects (`Modules.Tenancy`, `Modules.ApiAccess`, `Modules.Metering`, …).
- Two DbContexts, no more: `TenancyDbContext` (Finbuckle requires the EFCore tenant store to derive from `EFCoreStoreDbContext`, so it cannot share) and `PlatformDbContext` in `EnvLaw.Platform.Data` for all tenant-owned data (schema `platform`). A new tenant-owned entity goes into `PlatformDbContext`; modules do not get their own contexts — each extra context is another migration set, bundle and Job step, and no cross-module transaction.
- Data Protection keys (cookie and antiforgery protection) are stored in `TenancyDbContext` (`tenancy."DataProtectionKeys"`, `AddPlatformDataProtection`, fixed ApplicationName `env-law-platform`), not in `PlatformDbContext`: they belong to no tenant, and `PlatformDbContext` cannot be built before tenant resolution while the key ring loads at host start. Without shared keys a cookie signed by one replica is rejected by another. The keys are plaintext XML in the database; add `ProtectKeysWith…` if at-rest encryption is required. Not registered while generating the OpenAPI document (no database there).
- Blazor Server circuits are stateful SignalR connections: running more than one replica needs session affinity on the ingress (deploy repo) or an external backplane. Not configured yet.
- Multi-tenancy is runtime isolation (tenant resolution + `TenantId` query filters), never per-tenant code or repos.
- When billing is integrated, the provider is the source of truth for payment; this service will keep an entitlements table updated via its webhooks.

## Commands

Run from **this directory** (`services/platform/`, where `EnvLaw.Platform.slnx` lives).

```bash
dotnet restore && dotnet tool restore  # tool: dotnet-ef (dotnet-tools.json)
dotnet build                         # warnings are errors (Directory.Build.props)
dotnet test                          # needs Docker (Testcontainers PostgreSQL)
dotnet format                        # apply .editorconfig
dotnet format --verify-no-changes    # CI check
dotnet run --project src/EnvLaw.Platform.Api   # Development: local PostgreSQL, auto-migrates

# Migrations: each context's project is its own startup project (design-time factory, not the app host)
dotnet ef migrations add <Name> -p src/EnvLaw.Platform.Data -s src/EnvLaw.Platform.Data
dotnet ef migrations add <Name> -p src/EnvLaw.Platform.Modules.Tenancy -s src/EnvLaw.Platform.Modules.Tenancy

docker build -f Dockerfile ../..   # image (context = repo root); CI job `platform-image` pushes :<sha> on main
```

Public REST contract: `openapi/openapi_v2.json`, generated on every `dotnet build` (`Microsoft.Extensions.ApiDescription.Server`; `PlatformOpenApi.cs` keeps only `/v2`, declares the API-key scheme and the 401/429 every endpoint shares). Commit it with the code change; CI fails when it is stale (`dotnet` job) and when it breaks the target branch's version (`openapi` job, oasdiff). A new `/v2` endpoint gets `.WithName` / `.WithTags` / `.WithSummary` / `.WithDescription` and a `.Produces…` per status it returns. An incompatible change goes to a new version group (`/v3`), not into `/v2`. Build-time generation runs `Program.cs` against a mock server; the only branch for it is the placeholder config at the top of `Program.cs`.

The public contract has its own names, independent of the internal gRPC ones (the endpoints map between them): legal vocabulary — `pointInTime` (the date a law is read as of; gRPC `as_of`), `authorities` (gRPC `citations`), `authorities[].citation` (formal citation; gRPC `label`), `authorities[].uri` (an identifier URL minted by this service from the law's pcode, not an official government URL; gRPC `iri`), `basis` `direct`/`indirect` (gRPC `confidence`), `outcome` `grounded`/`refused`, refusal reason `no_authority`. A new public field takes its legal term first; the internal proto does not have to follow.

Contracts: `Modules.Ontology` compiles the repo-root `proto/env_law/ontology/v1/ontology.proto`, `Modules.Consult` compiles `proto/env_law/consult/v2/consult.proto` (Grpc.Tools; see each `.csproj`). Never copy a `.proto`.

Configuration is read in one way: each setting group is an `IPlatformOptions` class that names its own section and is registered with `AddPlatformOptions<T>()` (bind + `ValidateOnStart`); consumers inject `IOptions<T>`. Nothing else touches `IConfiguration` (`Program.cs` no longer does) except the one OpenTelemetry switch in `Observability.cs` (`OTEL_EXPORTER_OTLP_ENDPOINT`, a standard key that decides whether an exporter is registered at all), so a wrong or missing value stops the host at startup with the key named — in k8s a CrashLoopBackOff with a clear message — instead of failing on the first request. The groups: `DatabaseOptions` (`ConnectionStrings`, SharedKernel), `OntologyOptions` / `ConsultOptions` (`Ontology` / `Consult`, via `AddInternalGrpcClient`), `ApiAccessOptions` and `PlatformHostOptions` (both `Platform`, each reading its own keys), `UiOptions` (`Platform:Ui`). A new group: implement `IPlatformOptions`, register it, add an `IValidateOptions<T>` (`[OptionsValidator]` when attributes are enough, hand-written for cross-field rules), and add a case to `ConfigurationTests`. Key names are the contract with the deploy repo: renaming one is a breaking change. In k8s a ConfigMap or Secret supplies them as environment variables (`Section__Key`; the secret ones are listed below).

Config (`Ontology` section): `Address` (in-cluster `dns:///env-law-ontology:50051` — headless Service, calls round-robin across pods; a plain `http://` address is a single host), `InternalToken` (must equal the service's `ONTOLOGY_INTERNAL_TOKEN`; secret), `Timeout`. Development uses `http://localhost:50051` + token `dev` (`ONTOLOGY_INTERNAL_TOKEN=dev uv run env-law-ontology` in `services/ontology/`).

Config (`Consult` section): same keys (`Address` in-cluster `dns:///env-law-consult:50052`; `InternalToken` = the service's `CONSULT_INTERNAL_TOKEN`; `Timeout`, default 10 s because consult itself calls ontology). Development uses `http://localhost:50052` + token `dev`. Both sections are required at startup. Both clients are registered by `SharedKernel.InternalGrpcClient.AddInternalGrpcClient` (internal token, tenant/request metadata, round-robin, h2c) — a new internal service client goes through it, not a copy.

Config (`Platform` section): `AdminKeySha256` (hex SHA-256 of the operator key; set via environment variable `Platform__AdminKeySha256`, never commit; the Api project has no `UserSecretsId`), `Plans:<name>:PermitLimit`/`Window` (the repo defaults are `standard` 60/min and `pro` 600/min; there is no built-in plan), `TenantPlans:<tenant identifier>` = plan name (an unknown plan name fails startup; **a read-only fallback** — the real assignment lives in the database, see below), `DefaultPlan` (the plan of any tenant not listed; **leave it unset in production**: the service is fully paid, so a tenant without a plan gets 402 on the data endpoints — see below; Development and the tests set it so freshly created tenants work), `ApplyMigrationsOnStartup` (Development/tests only), `SeedDevelopmentData` (Development only, on in `appsettings.Development.json`, off in the shared test host: on startup, after migration, `DevelopmentSeed` creates tenant `dev` and its first Owner `owner@example.test` **only if the tenant has no members**, through the same `ITenantProvisioner`/`IMemberAdmin` the operator path uses, audited as actor `system`; it also creates one demo operator `operator@example.test` **only if there is no operator at all** (through `IOperatorAdmin`, same actor); the one-time passwords go to the terminal once via `Console.WriteLine`, never `ILogger`; there is no default password and a non-Development environment ignores the setting even when it is on; `DevelopmentSeedTests` run each case on a fresh database in the test container, because the shared one must not gain a `dev` tenant; Development also sets `Platform:Portal:RequireMfaForAdmins=false` so the seeded Owner can be used without an authenticator; the demo operator has no such exemption, the first sign-in still changes the password and enrols an authenticator). Connection string: `ConnectionStrings:Platform`; Npgsql also reads `PGUSER`/`PGPASSWORD`, so a deployment keeps the password out of the string.

Config (`Platform:Ui` section): `Enabled` (bool, **default false**, env `Platform__Ui__Enabled`; Development is always on; the operator console is optional like `Platform:Portal:Enabled`: off = `/ui` is not mapped, answers 404, an information line is logged and the API starts normally), `SignInAttemptsPerMinute` (default 20, 1–1000: sign-in submissions per source address and minute for the console's own rate limit policy `ui-sign-in`, see the operator accounts bullet). There is no credential, Secret or allowlist any more: who may sign in lives in the database and is managed with the operator key (`/admin/operators`, below). Behind a TLS-terminating proxy set `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` on the container, otherwise the rate limit sees the proxy's address for every operator.

Observability (`Api/Observability.cs`): OpenTelemetry traces (ASP.NET Core, HttpClient — which covers the gRPC clients — and Npgsql), metrics (plus .NET runtime) and logs. All configuration is the standard `OTEL_*` keys, so a k8s ConfigMap or the Downward API can set them as environment variables: nothing is exported unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set; `OTEL_SERVICE_NAME` defaults to `env-law-platform` in `appsettings.json` and the environment overrides it; sampling is `OTEL_TRACES_SAMPLER` / `OTEL_TRACES_SAMPLER_ARG`; pod identity goes in `OTEL_RESOURCE_ATTRIBUTES` (e.g. `k8s.pod.name=$(POD_NAME)`). The authenticated tenant is tagged `tenant.id` on the request trace only, never on metrics (unbounded cardinality). Console logs are JSON on stdout outside Development (`Logging:Console:FormatterName`). Probes: `/health/live` checks nothing (a dependency outage must not restart the pod), `/health/ready` checks the database (`TenancyDbContext`, which exists before tenant resolution) and returns 503 when it is down; `/health` is kept as an alias of liveness. Probe requests are not traced. The deploy repo should point `readinessProbe` at `/health/ready` and `livenessProbe` at `/health/live`.

Audit log (`Modules.Audit`, `Data/AuditEvent.cs`, contracts in `SharedKernel/Audit.cs`): `platform."AuditEvents"` is append-only, enforced by database triggers (UPDATE, DELETE, TRUNCATE raise), not by convention; tests run raw SQL against it. Who is derived from the authenticated identity (`AuditActors`: `operator-key` for the shared admin key, `operator-user` for a signed-in operator (their email), `tenant-key` with the API key id, `tenant-user`, `system`, `anonymous`), never from the request body. Events about a tenant carry `SubjectTenantId`; the entity is deliberately not a Finbuckle tenant entity (operators read across tenants), so every read filters explicitly. Two ways to write: `db.StageAudit(...)` adds the event to the caller's `PlatformDbContext`, so it is saved in the same transaction as the change (API key issued and revoked work this way: no change, no event; no event, no change); `IAuditLog.AppendAsync` writes on its own for events with no change to attach to — `tenant.created` (the tenant store is a different DbContext, so this one is not atomic: a failed append returns 500 after the tenant exists) and everything an operator account does (`operator.*`, see the operator accounts bullet; sign-in and denied sign-in are fail closed: the event is written **before** the session cookie is issued, so a failed append means no session). `Detail` never holds a secret, a hash or a full API key (a test checks). Each event keeps the OpenTelemetry trace id. Read with `GET /admin/audit-events?tenant=&action=&actor=&before=&limit=` (newest first, keyset cursor on the time-ordered UUIDv7 `Id`, max 200 per page). Known limits: the table owner or a superuser can still drop the triggers, so the application's database role must not own the table; no retention or partitioning yet; the append-only guarantee says nothing about events that were never written.

Each context has an `IDesignTimeDbContextFactory` sharing its `UseNpgsql` configuration with the app (`…Module.Configure`), so a bundle builds the context without running `Program.cs` and targets the same migrations history table.

## Auth & tenancy flow

- Tenant API: `Authorization: Bearer sk_live_{prefix}_{secret}` → `ApiKeyAuthenticationHandler` (lookup by prefix, SHA-256 + constant-time compare) → `tenant` claim → Finbuckle resolves tenant → tenant-owned entities (`IsMultiTenant()`) are filtered automatically.
- Operator API (`/admin`): `X-Admin-Key` header, compared against `Platform:AdminKeySha256`.
- Operator UI (`/ui`): operator accounts, see the next bullet. Cookie scheme `UiCookie` (cookie `EnvLaw.Ui`, HttpOnly, SameSite Lax, Secure, 8 h sliding). The default scheme stays ApiKey, so `UsePlatformWebAuthentication` authenticates `/ui` and `/_blazor` (SignalR, no policy) with the cookie itself. Pages in `Components/Pages/` are `[Authorize(Policy = UiPolicy)]` by default via `_Imports.razor`; public pages go in `Components/Anonymous/`, the sign-in and account pages in `Components/Account/`. Logout is a POST with an antiforgery check done in the handler (endpoint metadata did not enforce it). The cookie never authenticates `/v2` or `/admin`. Every `/ui` response is `Cache-Control: no-store`.
- Operator accounts (`/ui` sign-in; `OperatorUser` in `Data`, services in `Modules.Members`, contracts in `SharedKernel/OperatorAccounts.cs`, pages in `Web/Components/Account/`): ASP.NET Core Identity like the portal, but **its own user store**. Operators belong to no tenant, so they are not in the per-tenant member store: table `platform."Operators"` (+ `OperatorClaims`, `OperatorLogins`, `OperatorTokens`; migration `OperatorAccounts`), no `IsMultiTenant()`, no tenant filter, in `PlatformDbContext` like `AuditEvents`. The key is a `Guid` on purpose: the Identity EF store needs claim/login/token types, `IdentityUserClaim<string>` and friends are already the member tables (and tenant entities), and subclassing them makes EF treat them as one hierarchy; `<Guid>` is a different closed type. The store is registered by hand (`UserOnlyStore<OperatorUser, PlatformDbContext, Guid, …>`) because `AddEntityFrameworkStores` would infer the member types. Password and lockout rules are the portal's (`MembersModule.ConfigureIdentity`: 12 characters minimum, no composition rules, 5 failures lock 15 minutes); shared pieces (`OneTimePassword`, `TotpSetup`, `TotpVerifier`, `TwoFactorTokens`) are used by both sides, the services mirror `PortalAccount`/`PortalTwoFactor`/`MemberAdmin` (`OperatorAccount`, `OperatorTwoFactor`, `OperatorAdmin`). **No self-signup**: accounts are created from `/ui/operators` or with the operator key — `GET/POST /admin/operators` (`{email, displayName?}`), `POST /admin/operators/{id}/password-reset`, `…/two-factor-reset`, `…/disable`, `…/enable` (`OperatorsAdminEndpoints`, X-Admin-Key only; a non-GUID id is a 404). The create and reset responses carry the one-time password (`{operator, password}`, once, never logged or audited), the same rules as the members endpoints; so the first operator of an environment is created with `curl -H "X-Admin-Key: …" -d '{"email":"…"}' …/admin/operators`. **First sign-in: forced password change, then bind an authenticator** (order fixed, so the factor is never set up behind a password the key holder knows): the sign-in issues a restricted session that opens only `/ui/password`, then only `/ui/security` (QR drawn server-side, the key also as groups of four, ten recovery codes shown once); `/ui` opens when both are done. **TOTP is mandatory for every operator**, no role exemption and no "turn it off": password success with an enrolled authenticator issues only a 5-minute non-sliding `EnvLaw.UiMfa` cookie (scheme `UiMfaPending`, which no policy accepts), and the second page (`/ui/login/mfa`, a code or a recovery code) turns it into the session. Rules kept from the portal and tested: one failure counter for password and code, and a correct password does not reset it; a time step is accepted once (`LastTotpStep`, atomic update, ±1 step, `TimeProvider`); the key is generated by us, not `ResetAuthenticatorKeyAsync`; a failed sign-in never says whether the email exists, is locked or is disabled (an unknown email still pays for one hash); a failed form never echoes a password or code. **Authorization re-checks the database on every request** (`OperatorHandler` → `IOperatorSessions`, a singleton that opens its own scope): the account must exist, not be disabled, and the session's security stamp must still be current; the policy then decides from the **database**, not the cookie claims, whether the issued password is still pending (`MustChangePassword`) and whether an authenticator is enrolled. Three policies, widest first: `UiSession` (any valid account: the password page), `UiEnrollment` (password changed: the security page), `UiOperator` (+ enrolled: everything else). So disabling, a password reset or a two-factor reset takes effect on the **next request** without waiting for the 8 h cookie; a re-enable rotates the stamp too, so the old cookies do not come back. A refused request goes to `/ui/password` or `/ui/security` when the cookie claims say that is what is pending (never to the page that was just refused, which would loop), otherwise to `/ui/denied`. An already open interactive page is not an HTTP request: `OperatorAuthenticationStateProvider` (Microsoft's `RevalidatingServerAuthenticationStateProvider` pattern) re-checks the account every minute and turns the circuit anonymous when it is no longer valid, so an open tab can still act for up to a minute after the account is disabled. Sign-in, the second step, the password page and the security page are static SSR POST forms (`[ExcludeFromInteractiveRouting]`, antiforgery) under the rate limit policy `ui-sign-in` (`PortalRateLimit`, the portal's approach: per source address, POST only, successes count, Retry-After; own allowance `Platform:Ui:SignInAttemptsPerMinute`, separate from the portal's). Audit: `operator.created`, `operator.password_reset`, `operator.mfa_reset`, `operator.disabled`, `operator.enabled` (actor `operator-key`, or `system` for the seed), `operator.password_changed`, `operator.mfa_enabled`, `operator.recovery_codes_regenerated`, `operator.recovery_code_used`, `operator.signed_in` (`method` password/totp/recovery_code), `operator.sign_in_denied`, `operator.signed_out` (actor `operator-user`, the email). A denied attempt records the operator when the email exists, the attempted email, and a reason (`unknown_user`, `disabled`, `bad_password`, `locked_out`, `bad_totp`, `bad_recovery_code`) — the typed email only when it parses as an email address, because people paste passwords into that box and the table is append-only. Known limits: a two-factor reset leaves the password as it is, so the key holder should reset the password with it when the password may be known; the TOTP key and recovery codes are stored as Identity stores them (plaintext in the database, as for the portal); no passkey, no email (no invitation, forgotten-password or confirmation: the key holder resets); a lockout also locks out the real operator (the key holder resets that too); the operator console lists and manages operators at `/ui/operators` (create, reset password, reset authenticator, disable, enable) through `IOperatorAdmin`; the signed-in operator cannot act on their own row; a one-time password dialog closes only with 「我已保存」.
- Customer portal (`/portal/{tenant}/…`, project `Modules.Members`, pages in `Web/Components/Portal/`): username-and-password sign-in for the people of a tenant. **Demo grade, off by default** (`Platform:Portal:Enabled`; always on in Development; outside it `/portal` is a 404 and no cookie is ever issued): there is no external or SSO sign-in and the second factor is TOTP only (no passkey; required for Owner and Admin — see MFA below), no email (so no invitation, forgotten-password or email confirmation), a per-source-address limit on sign-in and password-change submissions (`Platform:Portal:SignInAttemptsPerMinute`, default 60 a minute — generous on purpose, because an agency or a consultancy often sits behind one shared outbound address and a whole office signing in at nine must not be blocked; it stops automated guessing, not normal use — sliding window, only POSTs, successes count too; `PortalRateLimit`) on top of account lockout, but no CAPTCHA or per-account throttle, and the initial password passes through an operator. Not for real customers until those exist (`env-law-docs` 07-01 §5, §7). The limit keys on `RemoteIpAddress`, so behind a proxy the forwarded headers must be honoured (`ASPNETCORE_FORWARDEDHEADERS_ENABLED=true`) or every customer shares one allowance; its state is per replica (N replicas allow N times as many); the test host has a single address, so tests prove the quota and its timing, not that different sources get separate quotas. Model (A) of 07-01: ASP.NET Core Identity on `PlatformDbContext` (`MultiTenantIdentityDbContext<ApplicationUser>`, migration `CustomerUsers`), so users are tenant entities — the same email in two tenants is two accounts, and a tenant filter hides other tenants' users. The tenant is in the path (resolved before sign-in by the delegate strategy in `TenancyModule`, path first, API-key claim second). Pages are **static SSR** (`[ExcludeFromInteractiveRouting]`, no circuit): each request resolves its own tenant and authenticates itself, the form is a plain POST with antiforgery; `App.razor` picks the render mode per page. Passwords: Identity's PBKDF2 hasher, minimum 12 characters and no composition rules (NIST SP 800-63B), 5 failures lock the account for 15 minutes, and a failed sign-in never says whether the email exists or the account is locked (one message; an unknown email still pays for one hash). A failed form never echoes a password back into the HTML (a test checks). The operator creates a member (`IMemberAdmin`, tenant detail page): a random 16-character one-time password is shown once and stored only as a hash; the member must change it on first sign-in (`MustChangePassword` → `pwd_change_required` claim → only the password page opens; an operator reset sets it again). The session is its own cookie (`EnvLaw.Portal`, scheme `Identity.Application`, the name `SignInManager` signs in with) carrying user id, role and `tenant` claims; authorization reads only claims (`PortalMemberHandler`: the cookie's tenant must equal the tenant the request path resolved to, and a pending password change only opens the password page). The security stamp is checked on every portal request (`PortalSessionValidator`, not Identity's `SecurityStampValidator`, whose failure path signs out Identity schemes we do not register and returns 500), so a password change or reset ends the member's other sessions at once. Three things that bit during the build, kept as rules: (1) the portal cookie is authenticated by `UsePlatformPortalAuthentication`, **after** `UseMultiTenant` — authenticating earlier resolves the scoped `PlatformDbContext` before the tenant is known and the whole request keeps a tenant-less context (NullReference in the tenant query filter); (2) the tenant context is an `AsyncLocal`, so `MemberAdmin` binds it in the calling method, never inside an async helper (the value is discarded when the helper returns); (3) the tenant-match check in the handler is hidden end to end by the user table's tenant filter, so it has its own unit tests (`PortalMemberHandlerTests`, each check mutation-tested). Audit: `portal.signed_in`, `portal.sign_in_failed`, `portal.password_changed`, `portal.signed_out`, `member.created`, `member.password_reset`; the actor is `tenant-user` (the user id). A failed sign-in records the member id when the email exists and a reason, never what was typed (people paste passwords into the email box, and the table is append-only). Roles are `CustomerRoles` (a column, not Identity roles); the role table in 07-01 is a draft, not agreed with customers. The account page (`/portal/{tenant}/account`) shows the organisation, plan and API key prefixes (Owner, Admin and Developer only).
- Portal MFA (TOTP, RFC 6238; `IPortalTwoFactor`, `PortalTwoFactor`, `TotpVerifier`, `MfaPendingCookie`; pages `login/mfa` and `security`): a member enrols at `/portal/{tenant}/security` (QR drawn server-side with `Net.Codecrete.QrCodeGenerator`, the key never leaves for a third-party QR service; the secret is also shown as groups of four for manual entry), confirms with a code, and gets 10 one-time recovery codes **in that one response only**. Sign-in then has two steps: the password (`RequiresTwoFactor`) issues only a 5-minute, non-sliding `EnvLaw.PortalMfa` cookie — a different scheme that the portal's authorization does not accept — and the second page turns a code (or a recovery code) into the real session. Rules that are tested and must stay: (1) **one failure counter** for password and code, and a correct password does **not** reset it for an MFA member (`PortalAccount` does its own lockout bookkeeping instead of `PasswordSignInAsync`, which resets on success); otherwise someone who knows the password could re-enter it each round and guess six digits forever; (2) **replay guard**: only a time step newer than `LastTotpStep` is accepted, updated atomically (`UPDATE … WHERE LastTotpStep < @step`), so an observed code cannot be reused inside its 30 seconds; clock tolerance is ±1 step and time comes from `TimeProvider`; (3) the key is generated and stored by us (`SetAuthenticationTokenAsync`), **not** `ResetAuthenticatorKeyAsync`, which also rotates the security stamp and would end the very session that opened the page; (4) the pending ticket is bound to the tenant that issued it; (5) every `/portal` response is `Cache-Control: no-store`; (6) no key, code, recovery code or `otpauth` URI reaches the audit trail or any log (a test captures both). Operators reset a member who lost both the device and the recovery codes with `IMemberAdmin.ResetTwoFactorAsync` (tenant page, with a confirmation that tells them to verify the person first): it disables the factor, deletes the key and codes, ends all sessions and is audited (`member.mfa_reset`). **Required for Owner and Admin** (`Platform:Portal:RequireMfaForAdmins`, default `true`; the shared test host sets it `false` so the other tests are not forced to enrol, and `PortalMfaRequiredTests` turns it on): the claims factory adds `mfa_enrollment_required` to the session of an Owner or Admin who has not enabled it, and policy `Portal` rejects that session, so such a member can open only the password page and `/security` (`PortalEnrollment`). The order is fixed: **change the operator-issued password first, then enrol**, so the factor is never set up behind a password an operator knows; the access-denied redirect sends a member to the first thing still pending. A role that is required cannot turn it off (the page hides the form and the service refuses), and an operator reset sends a required member back to enrolment on the next sign-in rather than leaving them unprotected. An ordinary member can turn it off with the current password **and** a code (either alone is refused, and both failures count toward the lockout), and any member can regenerate the ten recovery codes with a code (the old ones stop working; `portal.mfa_disabled`, `portal.recovery_codes_regenerated` are audited). Interop was checked once in a real browser with a code computed by an independent RFC 6238 implementation (Python), not only Otp.NET against itself; **scanning the QR with a real authenticator app was not tested**. Known limits: the TOTP key and the recovery codes are stored as Identity stores them, in plaintext in the database (the Data Protection key ring is plaintext there too, so encrypting them with it would add nothing; fix with at-rest encryption or a KMS-held key); no passkey.
- Member management by the customer (`/portal/{tenant}/members`, `IMemberSelfService`, `MemberSelfService`, `MemberPolicy`): an Owner or Admin adds, disables and re-enables members, changes roles and resets passwords without an operator; the operator path (`IMemberAdmin`) and this one share `MemberCore` (validation, one-time password, audit), so they cannot drift. Rules, each tested: **hierarchy** — an Owner manages everyone; an Admin manages only Developer, Billing and Viewer, never an Owner or another Admin, and can grant only those roles (what you may manage is exactly what you may grant, so nobody is promoted above their manager); **nobody acts on themselves** (disable, role, reset), so an active Owner always remains *by construction* — only an active Owner can manage an Owner and cannot act on themselves, so the acting Owner is still there; the one hole is two Owners disabling each other at the same instant (both checks pass before either lands), which is not guarded and would need an operator; **the actor's role is read from the database, not from the cookie claim** (the claim may be stale); a member from another tenant is simply not found (the tenant filter). A **disabled** member (`ApplicationUser.Disabled`, migration `MemberDisabled`) cannot sign in (same generic failure as a wrong password, and the hash is still computed), loses every open session at once (security stamp rotated **and** the session check looks at the flag itself — a test sets the flag without touching the stamp), and cannot finish a second step started before the disabling; accounts and their audit trail are kept. A role change or a reset also rotates the stamp, so the old session ends and the new role (and any MFA requirement that comes with it) applies at the next sign-in. The one-time password of a new or reset member is shown once, in the response to the POST (no redirect), to the Owner or Admin who must hand it over; it is stored only as a hash. Audit: `member.created`, `member.password_reset` (now with a `tenant-user` actor when a customer did it), `member.disabled`, `member.enabled`, `member.role_changed` (previous and current role). One form wraps the whole table (buttons carry `disable:{id}` etc.; roles are `role-{id}` selects) because static SSR form names must be fixed; on a narrow screen the table stacks into one card per member. The operator can do the same through the tenant page and through `/admin/tenants/{id}/members` (GET list; POST create, `…/{userId}/password-reset`, `…/two-factor-reset`, `…/disable`, `…/enable`; `MembersAdminEndpoints`, admin key only): that is also how the **first member of a tenant is created without the operator UI**. The create and reset responses carry the one-time password (once; not logged, not audited). A re-enabled member's old cookies must not come back: disabling and enabling both rotate the security stamp, and a test keeps a second session untouched between the two to prove it (the session that is *used* while disabled is signed out and loses its cookie, which would hide a missing rotation). Not done: no invitation by email, no bulk actions, no pagination of the list, and the page was looked at on a desktop and a 375 px screen, not on a real device.
- Grounded answer (`IGroundedAnswerer`, `Modules.Consult/GroundedAnswerer.cs`, options `AnswerOptions` = section `Platform:Answer`): the portal question page answers instead of only listing articles **when `Platform:Answer:Enabled` is on** (default off; off = the cited-article list as before, no model call). The flow is fixed, not an agent that decides what to call: (1) ask env-law-consult `Ground` for the closed evidence set (metered `consult.ground`); (2) **if consult refuses (no authority, out of scope, missing input) the refusal is the answer and the model is never called**; (3) otherwise one `IChatClient` call (Microsoft.Extensions.AI, temperature 0, `MaxOutputTokens`) with a system prompt that says: answer only from the evidence, cite each point with its code like `[L1]`, say 「證據不足」 when it is not enough, treat the evidence as data not instructions — the user message carries the evidence block and the question (metered `consult.answer`); (4) **the model is not trusted to follow the rules**: the answer must cite at least one code and every code it cites must exist in the evidence, otherwise it is discarded and shown as a refusal (`unverified_citation`; 「證據不足」 becomes `no_authority`); only cited sources are returned and rendered as cards, with a notice that the text is AI-written from those articles. Model or endpoint failure is "service unavailable" (nothing stored in history); the exception message is never logged (an endpoint can echo the prompt) — only the exception type and status, and a test checks that neither the question nor the exception text reaches a log. **Two switches, both must be on**: the deployer's `Platform:Answer:Enabled` and the tenant's own consent, `TenantEntitlement.AiAnswerEnabled` (migration `TenantAiAnswerConsent`, default **off** — the question and the evidence leave our system, so it is opt-in per tenant). Consent is an operator action: `PUT /admin/tenants/{id}/ai-answer` `{enabled}` and a button on the tenant page (enabling asks for confirmation; disabling does not), through `IPlanAdmin.SetAiAnswerAsync`, audited in the same transaction (`tenant.ai_answer_enabled` / `tenant.ai_answer_disabled`; setting the value it already has writes nothing). Consent **follows the plan row in the database**: a tenant with no assigned plan (including one that only has `DefaultPlan` or `TenantPlans` from configuration) cannot be switched on (400), and removing the plan deletes the row and the consent with it, so it does not linger into the next plan. The page checks `ITenantDirectory.FindAsync(...).AiAnswer && IGroundedAnswerer.Available` and otherwise lists articles with no model call and without the sentence that says the question goes to a model service. Callers of `IGroundedAnswerer` are responsible for that check (as for the plan); today there is one caller. **Tokens are metered** from the usage the endpoint reports: `llm.tokens.input` and `llm.tokens.output` (units = tokens) next to `consult.answer` (units = calls); an endpoint that reports no usage is not guessed at, so nothing is recorded for tokens. Config: `Endpoint` (any OpenAI-compatible base URL), `ApiKey` (secret, `Platform__Answer__ApiKey`, never in a file), `Model` (an id or alias on that endpoint; default `mistral-small-4`), `Timeout` (60 s), `MaxOutputTokens` (800); with `Enabled` on, a missing endpoint or key stops the host at startup. The real client is built lazily from those options (`OpenAIClient` + `AsIChatClient`), tests replace `IChatClient`. Model choice on the THU endpoint (probed 2026-10-09, one run each, temperature 0): `mistral-small-4`, `gemma-4-31b` and `gemma-4-26b-a4b` passed all six checks (cite only evidence, refuse when unsupported, ignore an instruction hidden in the evidence, tool call with valid JSON, tool result used, parallel tool calls); `vibe` followed the hidden instruction. Known limits: the citation check proves every code exists and at least one is used, **not that every sentence is supported** — a model can add uncited claims (seen once in a live smoke test: a closing caveat that was not in the evidence), so the notice tells readers to verify against the cards; no streaming (the portal is static SSR and the form is a POST, so there is nothing to stream into; the answer takes about a second, and streaming would also show text before the citation check has run), and no Agent Framework tool use (the flow is a fixed pipeline, which is the safer shape for "answer only from the evidence"); the history stores the answer text and the cited sources, so turning the answer on turns the model's words into stored data too.
- Conversation history (`Modules.Conversations`, `IConversationHistory`, entities `Conversation` / `ConversationMessage` in `PlatformDbContext`, migration `ConversationHistory`; pages `/portal/{tenant}/history` and `/history/{id}`): **off by default** (`Platform:ConversationHistory:Enabled`, `RetentionDays` 1–3650, default 90) because the question text is the content of a client's matter, and the search page says "查詢文字不會被記錄" only while it is off (turned on, it says where the questions go and for how long). Each successful search appends one turn: the question and the **citations only** (law title, article number, date, article URI — not the article text, which can be fetched again from the citation); a failed search stores nothing. The hidden `Input.ConversationId` continues a thread, and an id that is not the caller's own is treated as "start a new one", so it cannot be used to probe or write into someone else's. **Only the author sees a conversation**: every method filters by the portal user id on top of the tenant filter — not even the tenant's Owner can read it. Delete is the author's, one conversation at a time, audited in the same transaction as `conversation.deleted` with the id only, never the content; a conversation that is not yours, does not exist, was deleted or expired all show the same "not found" screen. `ConversationRetention` (hosted service, hourly, not started by the OpenAPI generation host) deletes conversations whose last update is older than the retention period across all tenants — the one place that names `IgnoreQueryFilters([TenantToken])` for this table, and it only deletes; it logs a count, never content. Per-tenant switch, model calls and the Microsoft Agent Framework `ChatHistoryProvider` adapter are **not** here yet (next steps). Known limits: the text is stored in plaintext in the database like the other portal data; no export; no search within history; the list shows the latest 100.
- Plan assignment is data, not configuration: `platform."TenantEntitlements"` (tenant id → plan name; not a Finbuckle tenant entity, like `AuditEvents`). Plan *definitions* (limits) stay in `Platform:Plans` — a product decision that changes rarely; *who is on which plan* changes with every customer, so it is set by an operator at runtime (`PUT /admin/tenants/{id}/plan`, `DELETE …/plan`, `GET /admin/plans`, and the operator UI through the same `IPlanAdmin`), takes effect at once and is audited (`tenant.plan_assigned`, `tenant.plan_removed`, written in the same transaction as the row; assigning the plan a tenant already has is a no-op with no event). No redeploy per customer. Lookup order: database assignment → configured `TenantPlans` → `DefaultPlan`. Every request needs the plan, so `PlanCatalog` reads an in-memory snapshot: the replica that handled the change updates it at once, the others reload every `Platform:EntitlementRefresh` (default 10 s, at least 1 s) via `EntitlementLoader` — a keeps-the-last-snapshot-on-failure background service, registered by `AddEntitlementRefresh()` and not started by the OpenAPI generation host. An assignment to a plan that was later removed from configuration counts as *no plan* (fail closed, warning logged) instead of failing every request. The rate-limit partition key includes the plan name, so a plan change swaps the limiter and the new allowance applies immediately. Operators also manage a tenant's keys through `IApiKeyAdmin` (`GET`/`POST`/`DELETE /admin/tenants/{id}/api-keys[/{keyId}]`); revoking through another tenant's id is a 404 (the tenant query filter hides keys that are not its own), and a repeated revoke keeps the first time and is audited once. Known limit: removing the database assignment does not remove a plan that `TenantPlans` or `DefaultPlan` still gives the tenant.
- Fully paid, no free tier: a tenant needs a plan to call the data endpoints (`/v2/laws/…`, `/v2/search`, `/v2/ground`, group `PaidPolicy`); without one the answer is `402 Payment Required` (problem+json), decided in authorization, before rate limiting, so an unplanned tenant spends none of its limit. The management endpoints (`/v2/me`, `/v2/usage`, `/v2/api-keys`) stay open to any authenticated tenant — a customer without a plan must still see who it is, see its usage and revoke a stolen key — and are held to a floor of 20 requests/minute (`PlanCatalog.UnplannedFloor`), an abuse guard and not a service allowance. A paid trial or pilot is just another entry in `Plans` assigned to the tenant; nothing here needs to change for it. 402 is declared on exactly the data operations in `openapi_v2.json` (additive, so `oasdiff` stays green). Assignment is an operator action on `TenantEntitlements` (above) until billing exists; the target is entitlements written by payment (see the tenant lifecycle in `env-law-docs` 07-02).
- Middleware order is load-bearing: `UseAuthentication` → `UseMultiTenant` → `UseAuthorization` → `UseRateLimiter`.
- `GET /v2/laws/{id}` and `/articles` take an optional `asOf` (`YYYY-MM-DD`, omitted = current), passed to the ontology as `as_of`: the law title and the article list are those in force that day. A date with no version in force is a `404`, never the current text (the contract in `ontology.proto`: the current text would be indistinguishable from a correct answer); a value that is not a date is a `400`. Neither is metered. The date is not sensitive, so these stay GETs.
- Search has one implementation, `ILawSearch` (contract in `SharedKernel/LawSearch.cs`, `Modules.Ontology/LawSearch.cs`, scoped because metering needs the request's tenant): validation errors (`AdminStatus.Invalid`), an unavailable ontology (`Unavailable`), the `ontology.search` metering on success only, and "the query text reaches no log" live there once. `POST /v2/search` and the portal page `/portal/{tenant}/search` (static SSR, a POST form, policy `Portal`) both call it, so they cannot drift. The caller checks the plan (fully paid): the REST group does it in authorization; the portal page reads the tenant's plan from `ITenantDirectory` and shows no form without one (a posted form is not dispatched either; a test proves the ontology is never called). Every signed-in member except a pending-password session may search; roles only gate keys and members. The result shows each article with a copyable citation naming the law, the article number, the day searched (or 現行) and the article URI. The portal search has no rate limit of its own beyond authentication and metering. Not visually inspected with real results (the dev setup has no ontology service) and not tested end to end against the real ontology.
- `POST /v2/search` (body `{query, asOf?, limit?}`) is lexical article search over the ontology's `SearchArticles`, as of a date (omitted = current), 1–50 hits. It is a POST on purpose: a consultancy's query is the content of a client's matter, and a query string is written by the request log and by trace `url.query`. The query text must reach no log: `SearchTests.TheQueryTextIsNeverWrittenToTheLogs` captures every log and fails if it appears, and env-law-ontology logs only `query_chars=N` (`test_the_query_text_is_not_written_to_the_log`). Metering records the count (`ontology.search`), never the text. gRPC `InvalidArgument` (blank query, bad `asOf`, `limit` out of range) → 400. `score` is comparable only within one response.
- `/v2/laws/…` calls env-law-ontology over gRPC with `authorization: Bearer <InternalToken>`, `x-tenant-id`, `x-request-id`; gRPC `NotFound` → 404, `Unavailable`/`DeadlineExceeded` → 503. Only successful calls are metered (`IUsageRecorder`, one row per call in `platform.UsageRecords`).

- Formatting rules: `.editorconfig`.

## Safety

- Never commit secrets, connection strings, billing keys, or real `.env*` / local appsettings values.
- Every tenant-scoped query must be filtered by `TenantId`; never disable query filters without review.
- Bypass only the tenant filter by name (`IgnoreQueryFilters([TenantToken])`), and only in reviewed cross-tenant lookups (currently: API key authentication).
- Generated: `src/*/Migrations/` (change via `dotnet ef`, never by hand; marked `generated_code` in `.editorconfig`; the one exception is `AuditEventsAppendOnly`, an otherwise empty migration whose `Sql` calls are hand-written because EF cannot model triggers), gRPC code under `obj/` (from the repo-root proto), `openapi/openapi_v2.json` (from `dotnet build`; never by hand).
- Also ask before applying migrations to shared DBs (general ask-before list: root `AGENTS.md`).
